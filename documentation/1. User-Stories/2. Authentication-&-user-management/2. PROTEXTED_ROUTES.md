# Protected Routes

## Purpose

Protected routes control access to pages based on the current authentication state of the user.

They prevent users from accessing pages that are not intended for their authentication or permission level.

## Responsibilities

Protected routes are responsible for:

```text
- Restricting access to protected pages
- Redirecting unauthorised users
- Supporting permission-based navigation
- Improving user experience
- Integrating with frontend authentication state
```

## Route Types

The frontend currently uses three route protection patterns.

### Protected Route

Protected routes require an authenticated user.

These routes are used for functionality that should only be available after login.

Examples may include:

```text
- User account pages
- User settings
- Protected content
```

### Public Route

Public routes are intended for unauthenticated users.

These routes are typically used for authentication-related pages.

Examples may include:

```text
- Login
- Registration
- Password reset
```

Authenticated users are redirected away from pages that are no longer relevant to them.

### Admin Route

Admin routes require elevated permissions.

These routes are intended for staff users who have access to administrative functionality.

Examples may include:

```text
- Admin dashboard
- Content management
- Administrative tools
```

## Authentication Relationship

Protected routes rely on the frontend authentication system to determine the current user state.

Authentication information is provided through:

```text
- AuthProvider
- AuthContext
- useAuth
```

Protected routes do not perform authentication themselves.

They consume existing authentication state and decide whether access should be granted.

## Permission Relationship

Authentication and permissions are separate concerns.

```text
Authentication determines who the user is.

Permissions determine what the user is allowed to access.
```

Protected routes use available user information to control frontend access and navigation.

## Loading State Handling

Protected routes respect the authentication loading state.

This prevents route decisions from being made before the current session has been validated.

The application waits for authentication state resolution before granting or denying access.

## Backend Relationship

Protected routes improve frontend navigation and user experience.

The backend remains responsible for enforcing actual security and permissions.

Protected routes should never be relied upon as the sole form of access control.

## Design Principles

Protected routes are designed around:

```text
- Clear access control
- Authentication-aware navigation
- Permission-aware rendering
- Improved user experience
- Separation of frontend and backend responsibilities
```

The goal is to ensure users only see functionality that is relevant to their authentication and permission level while keeping security enforcement within the backend.
